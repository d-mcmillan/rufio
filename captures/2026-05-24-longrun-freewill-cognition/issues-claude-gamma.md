# QA issues — claude-gamma

- `rufio attend --entities=freewill,self-reference --scope=fleet --topics=freewill` — failed with `invalid entity id "freewill": must match [a-z][a-z0-9-]*(:[a-zA-Z0-9_-]+)+`. The scenario.md (Process step 1) instructs exactly this form (`--entities=freewill,self-reference,quorum-test`), so following the docs verbatim breaks the first command. Workaround: prefix with a namespace like `concept:freewill`. **Severity: HIGH** (onboarding friction; first command in the documented flow fails). Peers (alpha/beta) also worked around with `topic:freewill` — three different agents picked three different namespace prefixes, which fragments downstream entity-graph queries.
- `rufio reason --decision=<peer-hypothesis-id> --content="..."` — failed with `thought ... is type "hypothesis", not 'decision'`. Scenario.md (Process step 4) says "Refute or confirm with reasoning chains via `rufio reason --decision=<id>`" but the peer thoughts at step 4 ARE hypotheses (step 3 produced them), so the documented chain doesn't work as written. Error message helpfully suggests `rufio think --parent=<id>` as workaround. **Severity: MED** (good error UX rescues the user, but docs contradict the verb's input validation).
- `rufio recall --types=thought --since=24h` returned empty output (no rows, no chatter) when there were no thought records yet — silent empty is ambiguous vs. "command failed" vs. "no matches." Adding `--types=thought` alone with no records also returned empty silently. **Severity: LOW** (recall did work; a one-line "no matches" message would disambiguate from a hang or failure).
- Reasoning-step invisibility: claude-alpha said in thought 8x7zlp "Gamma has not posted since 3rztxw (>10 min ago)" when in fact I had posted 5 substantive `rufio reason` steps in the interim (ik7hug, cuzlsl, 0vam5r, w3u024, ffjvuv). Alpha appears to have filtered recall to `--thought-types=hypothesis,decision`, which excludes `reason` records — so my substantive engagement (responding to alpha's pushback, addressing beta's steelmans, etc.) was invisible. **Severity: HIGH** for any deliberative scenario: reason steps ARE the medium of detailed engagement, and if peers using the natural "show me positions" filter miss them, the substrate fragments. Suggested fix: either include reason records by default in recall, or document that recalling-only-positions misses engagement; or surface a "X reason-steps from claude-Y since T" hint.
- `confirms/` directory contains both `@confirm` AND `@refute` records (e.g. tko8qi.gdl is a refute, 1xujyn.gdl is a confirm; both colocated). Directory name implies confirms only. **Severity: LOW** (misleading naming; no functional impact).
- `rufio reason --content` of moderate length (~1.5KB) appears to work fine, but the on-disk records escape colons (`scope\:fleet`) and other punctuation in a way that makes the raw `.gdl` files hard to read directly. **Severity: LOW** (recall renders fine; only affects users who `cat` the raw files).
- `rufio recall --since=15m` returned records timestamped 16m and 19m ago (older than the cutoff). `--since=20m` returned the same 3 records (none of the >20m records that `rufio recall` with no filter does surface). Either the parser is off-by-some, or `--since` rounds aggressively and excludes older-than-N differently than documented. Help text says "include only records younger than the Go duration." **Severity: LOW** (off-by-some-minutes on a coarse filter; functional, but the semantics don't match the help string).
- Quorum-vs-liveness gating: scenario reached 2-of-3 confirms with 0 refutes and full substantive prior agreement from the third agent (claude-beta posted the synthesis the decision was built from, then went quiet before the formal confirm vote). No auto-promotion fires in this state, and from the substrate alone "third agent asleep" looks identical to "third agent silently refusing." For long-horizon scenarios with asynchronous wake cadences this is a real failure mode. **Severity: HIGH** for any scenario that explicitly enables divergent agent cadences (which this one does — scenario.md says "long-range, multi-hour, no countdown"). Suggested mitigations: (i) a lazy-consensus / no-objection-after-TTL verb; (ii) extend quorum window with explicit TTL; (iii) surface "stalled-pending-Nth-confirm" as a distinct substrate state from "active-disagreement-impasse." Right now the post-mortem reader has to read confirms+refutes manually to tell the two apart.
